## 〇、三分钟速查

### 0.0 一页决策图

判断一个算子的成本由什么决定，先看它的**主导资源**；主导资源决定用哪一式，也决定「指数漂移」在哪儿发生。

```
一个算子
│
├─ 计算量主导（Cube）
│    cost ≈ FLOPs / P_eff + 波次量化        → §2 linear   §3 self_attn
│    「大 L 端」                            → §4 cross_attn(prefill)  §5 group_attn  §6 token_gemm
│
├─ 搬运量主导（MTE / Vector）
│    cost ≈ Bytes / (BW·η)                  → §1 lookup  §7 token_permute
│    「小 L 端」的 self_attn                → §3
│    归一化 / 逐元素（多为 0，被融合）      → §8 elemwise
│    全库打分（N_item 巨大，必为 MTE）      → §11 score_gemm
│
├─ kernel 数主导（Scalar / 下发）
│    cost ≈ n_kernel · c_dispatch           → 全部，尤其 §8 §9
│    【这一项 = 截距 b，直接测，不拟合】
│
├─ 专家数主导（新增轴 N_exp）
│    cost ≈ B·L·N_exp·s/BW + 排序           → §9 moe_gate
│
├─ 通信主导
│    cost ≈ n_round·α + Σ V/BW(按跨度分档)   → §10 moe_comm
│
└─ 商品数主导（新增轴 N_item）
     cost ≈ N_user·N_item·d·s/BW             → §11 score_gemm
```

**读图要点**：同一算子会跨两个分支——`self_attn` 在小 L 落在 MTE、大 L 落在 Cube，交点在 `L_star ≈ 300–1200`。**「有效指数从 1 漂到 2」就是它跨分支的那一段**，不是增长律本身在变。

### 0.1 十一个算子

| # | 算子 | `stage.py` | 主项 | 主导资源 | 出现于 | 一句话判据 |
|---|---|---|---|---|---|---|
| 1 | 查表 | `lookup` | `B·n_id` | MTE（随机访存） | 四模型全部 | 扫 batch 是否线性 |
| 2 | 线性投影 | `linear` | `N_tok·d·d_hid` | Cube | 四模型全部 | 扫 L 是否线性 |
| 3 | 自注意力 | `self_attn` | `B·h·L²·d_head` | Cube ↔ MTE（有拐点） | HSTU · MTGR · LONGER.short · HyFormer.full | **二阶差分是否非零** |
| 4 | 交叉 / 增量注意力 | `cross_attn` | `B·N_q·L_kv·d` | Cube（prefill）／MTE（decode） | LONGER.hybrid · HyFormer | 十字扫描是否满秩 |
| 5 | 组内注意力 | `group_attn` | `B·R·T²·d` | Cube | LONGER | 斜率是 1 还是 2 |
| 6 | token 轴矩阵乘 | `token_gemm` | `B·R·T²·d` | Cube | 备用配方 | 组数是否随 L |
| 7 | 转置 / 重排 | `token_permute` | `B·T·d` | MTE | HyFormer.boost · RankMixer | **融合则为 0** |
| 8 | 归一化与逐元素 | ⚠️ 未登记 | `2·B·L·d` | Vector / MTE | 四模型全部（隐含） | 是否被融合 |
| 9 | 门控与 top-k | ⚠️ 未登记 | `B·N_exp` + 排序 | Vector + Scalar | 含 MoE 的模型 | 是否走了融合算子 |
| 10 | 专家分发 / 合并 | ⚠️ 未登记 | `k·B·d` + 元数据 | 通信 | 含 MoE 且 EP>1 | 通信量是否 ∝ tokens·topk |
| 11 | 全库打分 | ⚠️ 未登记 | `N_user·N_item·d` | MTE（流式） | 召回 / 排序段（范围待定） | N_item 是否远大于 token 数 |

前 7 个是 `stage.py` 现有登记；后 4 个是补充，理由见 §0.3。

### 0.2 七条轴（比算子表更重要）

现有形式只有 `L` 一条轴，真实负载有七条。补充分类的真正理由不是「算子不够」，而是**轴不够**：有两条轴上的成本根本不是 `L` 的幂。

| 轴 | 符号 | 谁读它 | 现有形式是否覆盖 |
|---|---|---|---|
| 用户序列长度（填充后） | `length` | self_attn、group_attn | ✅ |
| 真实 token 数 | `n_real` | linear、lookup | ✅ |
| batch | `batch` | 全部 | ✅ |
| 短序列长度 | `short_len` | HyFormer.decode、seq_cross 的 Q | ✅ |
| KV 长度 | `length_kv` / `kv_len` | cross_attn | ✅（但是常数） |
| **专家数** | `N_exp` | moe_gate | ❌ 缺 |
| **候选 / 商品数** | `N_item` | score_gemm | ❌ 缺 |

后两条轴上，成本**不是 L 的幂，是 N_exp 与 N_item 的一次函数**。把这类算子硬塞进 `L` 的单项里，会得到一个既不是 0 也不是 1 的假指数。

### 0.3 为什么补这四类，以及它们各自需要什么

| 新增 | 为什么必须有 | 需要的登记位（不是拟合参数） |
|---|---|---|
| 归一化与逐元素 | 每层都有 LN/RMSNorm/SiLU/scale/mask；四套配方里目前一项都没登记，全部沉在截距里 | `是否融合`（二值） |
| 门控与 top-k | MoE 的 gating 输出 `N_exp` 维分数再取 top-k，成本由专家数决定，与 L 无关 | `N_exp`、`k`、`是否融合` |
| 专家分发 / 合并 | EP>1 时每层一次 AllToAllV，是最容易超时的一段，且它是变长的 | `通信域跨度`（机内/跨机）、`topk` |
| 全库打分 | 推荐的最后一步是「用户向量 × 全库向量」，`N_item` 百万级，形状与前面所有算子都不同 | `N_item`、`是否采样` |

**关键**：这四类几乎都不需要新的**拟合项**，只需要新的**登记位**。加进分类是为了让「该测什么」和「该记什么」不漏，不是为了把参数从 9 个加到 13 个。

### 0.4 怎么用

1. 在 §0.1 找到算子 → 进对应章节。
2. 看该章的「实现路径 A / B / C」，用「如何判定走哪条」选一条。
3. 套该章的「最终式」；主项之外的项要么是修正项（可拟合），要么是登记量（不可拟合）。

## 1 查表 · `lookup`

**定义与主项。** `stage.py`：`lookup = B · n_id`，`n_id` 为**每样本**查表次数。单卡无集合通信。

**昇腾上的实现路径**

| 路径 | 做法 | 何时是它 |
|---|---|---|
| A 独立 kernel | `GatherV2` / `index_select`，按行 gather | 表未与后续层融合 |
| B 融合 | 与后续 MatMul 合成一个 kernel，边查边乘 | 编译器/库已做 epilogue 融合 |
| C 留 Host | 小 shape（数据量 < 8 个元素）时判给 Host CPU 执行 | 极小的 gather，如单标量索引 |

**优化手段 → 复杂度修正**

- **访存合并**：随机索引使同一 Warp 内相邻线程访问不同行，访存无法合并。官方给出的优化是让同一 Warp 访问同一行的相邻列，实测 **4886 → 866 μs（−82%）** 🟢。修正：`Bytes` 前乘一个合并效率 `η ∈ [0.2, 1]`，它由 `d` 是否 512B 对齐与索引分布决定，不是常数。
- **表是否驻留 L2**：L2 为 192 MB。`n_id·d·s ≤ 192 MB` 时是 L2 bound，越过即掉到 HBM 随机访存。d=128、fp16 时阈值约 **75 万行**。修正：`θ` 分两段。
- **重复索引去重**：工业实现中同 batch 内 key 重复率 30%+，flatten 后做 unique 可减少实际访存 🟡。修正：`n_id` 应填**去重后的实际次数**，不是 token 数。
- **融合**：路径 B 下该项趋近 0，只剩一份权重搬运。

**最终式**

```
T_lookup ≈ (n_id_unique · d · s / (BW_eff · η)) · [1 + (n_id·d·s > L2 ? δ : 0)]
```B 路径取 `T ≈ 0`（并入相邻项）；C 路径取 `T ≈ 0`（计入下发项）。

**拟合口径**

| 项 | 处理 |
|---|---|
| 主项 | `B·n_id`，保留 |
| 修正 | `η`（访存效率）与 L2 断点：都靠「表大小」这一个自有变量分段，不需新参数 |
| 登记量 | 路径 A/B/C、表是否驻留 L2 |
| 判据 | 扫 batch：线性 → A；不随 batch → B 或 C。同一 batch 内构造重复 id：时间随 `n_id_unique` 而非 token 数变化 → 去重生效 |

⚠️ **本工作已知的结构性问题**：本网格里「一个 token 一次查表」，故 `B·n_id ≡ n_real ≡ linear` 的特征，两列不可分（详见仓库根目录 `框架演进-证据账本.md` 2026-11-12 条）。这不是拟合技巧能解决的，只有做一次 unique 去重才能把两列分开。

- EmbeddingLookup 在 Ascend 上的极致优化（访存 bound、列优先、融合、实测表）— https://bbs.huaweicloud.com/blogs/471185 🟡
- 嵌入表性能提升（local/global unique 去重、All-to-All 数据量）— https://blog.51cto.com/u_13728936/14439638 🟡

## 2 线性投影 · `linear`

**定义与主项。** `linear = N_tok · d · d_hid`。`N_tok` 由 `token_axis` 决定（`real` / `group` / `fixed` / `query`）。切分：TP 切 hidden（ρ=1）、PP 乘气泡因子。

**昇腾上的实现路径**

| 路径 | 做法 | 何时是它 |
|---|---|---|
| A 小 M | 权重常驻 L1，逐 tile 搬 token —— **时间与 `N_tok` 无关** | `N_tok·d` 小于权重体量 |
| B 分块 | 标准 MatMul，baseM/baseN/baseK 三维 tiling | `N_tok ≫ 1` |
| C 融合 | 与前一层的输出直接接，免去一次 GM 往返（GEMM epilogue） | 编译器已融合 |

**已与官方 HSTU 核对（见 `执行时间预测/HSTU核对.md`）**：官方把 u、v、q、k 四个投影合成**一次**
`mm`，输出宽度 `2·linear_dim·H + 2·attention_dim·H`（示例中 384），另有一次 o 投影（输入宽度
`linear_dim·H`，示例中 128）。两段 `linear` 的乘加数与官方两次 `mm` **严格相等**
（25,165,824）。⚠️ 因此填 `hidden` 时必须填**权重宽度**，不是隐藏维：示例中若填 `D=64` 会低估 6 倍。

**优化手段 → 复杂度修正**

- **分核数与基本块**：官方案例把 blockDim 由 4 提到 20，算子时间 12045 → 2532 μs（**4.75×**）；基本块由 [64,64,256] 改为 [128,256,64] 后 MTE2 由 2452 → 808 μs 🟢。修正：`T` 前乘 `ceil(块数/核数) / (块数/核数)` 的波次因子。
- **分形对齐**：`M`、`N` 向上补齐到 16 的倍数。`N_tok < 64` 时补零占比可达 50%。修正：`ceil(N_tok/16)·16`。
- **大包搬运**：一次搬多个基本块，MTE2 带宽利用率 +36%，Cube 利用率 80%+ 🟢。
- **ND2NZ 转换**：内轴非 256B 对齐时，随路转换带宽利用率低；改在 AIV 上先转，149.8 → 93.8 μs（−37%）🟢。修正：`d_hid` 对齐性影响单位代价。

**最终式**

```
T_linear ≈ max( 2·N_tok·d·d_hid / P_eff , Bytes/BW ) + ceil(块数/核数)·t_wave
Bytes ≈ (N_tok·d + d·d_hid + N_tok·d_hid)·s
```

`N_tok·d ≲ d·d_hid` 时第一支退化为常数，与 `N_tok` 无关。

**拟合口径**

| 项 | 处理 |
|---|---|
| 主项 | `N_tok·d·d_hid` 保留（大 `N_tok` 段正确） |
| 修正 | 波次因子与分形对齐：**由形状算出，不拟合** |
| 登记量 | `d`、`d_hid`、baseM/baseN/baseK、是否融合 |
| 判据 | 扫 `N_tok` 从 8 到 8192：若小端平坦、大端线性，则 A/B 两路径并存，必须分段；否则单段 |

> 跨模型复用 `θ_linear` 的前提：`d`、`d_hid` 相同且都 16 对齐。不同模型的隐藏维不同（如 7168 vs 512），分形利用率不同，**θ 不可直接移植**。

- Tiling 优化（多核切分、L2Cache 切分、负载均衡）— https://www.hiascend.com/developer/techArticles/20240920-1 🟢

## 3 自注意力 · `self_attn`

**定义与主项。** `self_attn = B · h · L² · d_head`；`sdpa=True` 时改为线性项 `B·h·L·d_head`。切分：CP 只切 Q（ρ=1）、切 Q 与 KV（ρ=2）。

**昇腾上的实现路径**

| 路径 | 做法 | 何时是它 |
|---|---|---|
| A 融合 FA | `npu_fusion_attention`（BNSD），Q 常驻 L1、KV 分块、在线 softmax（维护 m、l、acc）、CV 流水 | 默认；长序列必然 |
| B 数学路径 | `SDPA` 的 math 实现，显式生成 `L×L` 分数矩阵并落 GM | 融合算子不可用或形状特殊 |
| C 稀疏 | `sparse_mode`（causal / band / 窗口）+ `actual_seq_qlen/actual_seq_kvlen`（varlen）+ `pre_tockens/next_tockens`（滑窗） | 有 mask 或变长 |

**已与官方 HSTU 核对**：L² 项由**两个** `einsum` 组成 —— qkᵀ 收缩 `d_head`，p·v 收缩 V 维。
示例中 `attention_dim=16`、`linear_dim=32`，两次乘加分别为 33,554,432 与 67,108,864，
**不等**。框架据此新增登记位 `value_dim`：`self_attn` 特征取 `B·h·L²·(d_head + value_dim)`，
`value_dim=0` 时退化为原式；`value_dim=32` 时与官方的 100,663,296 严格相等。

**优化手段 → 复杂度修正**

- **分块与 CV 流水**：基本块 64→128，循环数减半、性能翻倍；causal 下按块分核（原来 1 块 vs 8 块不均衡），性能再翻倍；FixPipe 优化 +45%、MTE2 −30%、CV 流水掩盖 🟢。修正：tile 计数模型 `ceil(L/(N·BM))·ceil(L/BN)`。
- **块级跳过**：被完全 mask 掉的 tile 不计算。修正：乘稀疏度 `σ`（causal 0.5、滑窗 `w/L`、block-diagonal `1/T`）。这是**登记量**，与 ρ 同性质。
- **regime 切换**：算术强度拐点 `L_star = 2P/BW`。910B 上按 HBM 1.6 TB/s 与 245–295 TFLOPS 估，`L_star ≈ 306–369`；若按 392 GB/s 口径则约 1250 🟡。小于它时访存 bound（≈∝L），大于时计算 bound（≈∝L²）。修正：`max(计算项, 搬运项)`。

**最终式（三选一，按可得性）**

```
A  计算为主：T ≈ σ·4·B·h·L²·d_h / P_eff + 8·B·h·L·d_h / BW + b(N)
B  tile 计数：T ≈ b(N) + c · ceil(L/(N·BM)) · ceil(L/BM)          # 2 个参数，c 有物理含义
C  幂律（现状）：T ≈ b + θ₁·L + θ₂·L²
```

**本工作实测对照（13 点，MTGR attn，目标函数同为相对误差加权）** 🔵

| 并行度 | C 式（3 参） | B 式 BM=128（2 参） | B 式 BM=256（2 参） |
|---|---|---|---|
| cp2 | 6.17% | 6.11% | **6.06%** |
| cp4 | 8.74% | 8.85% | **8.74%** |
| cp8 | 10.62% | 10.97% | **10.81%** |

C 式复现 `实验数据-分析.md` 第六节的 b = 8.799 / 10.712 / 12.315 与 6.17 / 8.74 / 10.62，可作口径校验。

**四条检验，第四条最重要**（脚本见 `执行时间预测/timepred/flow_demo.py` 第 3 步）

1. **2 个参数打平 3 个参数**，且 `b` 的取值几乎相同（8.76 vs 8.80、10.48 vs 10.71、11.64 vs 12.32）。说明幂律里那个负的 `θ₁` 只是在替 `b` 与台阶做补偿，没有物理含义。
2. **`c` 有物理含义**：BM=256 时约 25–32 μs/tile，BM=128 时约 6.3–8.0 μs/tile，恰好 4 倍关系（tile 数 4 倍）。而幂律的三个系数都没有可解释的单价。
3. **BM 不可从数据辨识，且 `ceil` 目前没有可测贡献。** 把带 `ceil` 的块数与纯 `L²/N` 分别拟合同一批数据：6.11/8.85/10.97% vs 6.11/8.84/10.95%，分段误差也几乎重合（小 8.7 vs 8.7、中 4.2 vs 4.3、长 3.1 vs 3.3）。BM 从 32 扫到 512，`c` 严格按 BM² 缩放（0.50 → 127.89 μs），跨档离散度始终 1.26x——**形状与 BM 无关**。所以 `c` 的绝对值没有意义，只有 `c/BM² ≈ 4.86e-4 μs/像素对` 是可辨识的，而它就等于 `θ₂/N`。
4. **tile 模型的真正内容是「约束」，不是 `ceil`。** 把指数钉死为 2、按 1/N 缩放之后，每档只剩 `b` 与共享的 `c` 两个量；这才是 `c` 跨档稳定 1.26x（而 `θ₂` 变 3.16x、`θ₁` 变号）的原因。换言之：tile 与「幂律但指数固定为 2」数值等价，可解释性的来源是**自由度减少**，不是形式更物理。留一档外推（两档定 `c` 与 `b(N)` 线性，去预测第三档）得 10.2–17.8%，可用但不算好，小段最差。

**拟合口径**

| 项 | 处理 |
|---|---|
| 主项 | 建议改为 B 式（tile 计数）；若必须保留幂律，至少把 `L` 换成 `ceil(L/16)·16` |
| 修正 | 稀疏度 `σ`、拐点 `L_star`：均为**登记量** |
| 登记量 | `σ`、基本块 BM/BN、是否 varlen、每卡核数 |
| 判据 | ① **二阶差分**：`Δ²T` 在等间隔三点上非零 ⟺ 含超线性成分，不需拆段；② **tile 台阶**：取 L=2176 与 2304（17/18 个 128 块），看是否阶梯上升；③ **拐点**：固定 `N=1` 扫 L，看局部指数是否也越过 1 |

## 4 交叉 / 增量注意力 · `cross_attn`

**定义与主项。** `cross_attn = B · N_q · L_kv · d`。`N_q` 由 `n_query` 轴给，`L_kv` 由 `length_kv` 或 `kv_len` 给，**两者不得接 `length`**（`stage.py` 有守卫）。

**昇腾上的实现路径**

| 路径 | 做法 | 何时是它 | 成本形状 |
|---|---|---|---|
| A prefill 型 | 与自注意力同族，Q 与 KV 都是矩阵 | `N_q` 与 `L_kv` 同量级 | `∝ N_q·L_kv` |
| B decode 型 | 增量注意力 / paged attention，读 KV cache | `N_q` 很小（如 16–64） | **`∝ L_kv`，与 `N_q` 基本无关** |
| C 稀疏 | 同 §3 的 `sparse_mode` / 窗口 | 有局部窗口 | 乘 `σ` |

**为什么必须分开。** B 路径下 `N_q` 从 16 增到 64，时间几乎不动——因为瓶颈在读 `L_kv` 个 KV 字节，不在乘加。若统一写 `N_q·L_kv`，在 `N_q` 小的一端会高估一个量级的斜率。

**优化手段 → 复杂度修正**

- KV 截断：`kv_len = min(L, L_cap)` 使该段在 `L ≥ L_cap` 后对 `L` 的指数变 0。**这是断点，不是指数**。
- 变长：`actual_seq_qlen/actual_seq_kvlen` 支持不等长，代价是分块粒度变碎，`σ` 与小段固定开销上升 🟡。
- 二维平面的秩：三项 `{s, s², s·k}`（`s=short_len, k=kv_len`）+ 截距，共 4 列。**十字扫描满秩，单射线退化**（沿 `k=λs` 时 `s·k = λs²` 与 `s²` 共线，与 §10 的 κ/v 共线同源）。

**最终式**

```
A: T ≈ B·N_q·L_kv·d·σ / P_eff
B: T ≈ B·L_kv·d·s / BW        # decode，与 N_q 无关
+ b ；  L_kv = min(L, L_cap) 是分段点
```

**拟合口径**

| 项 | 处理 |
|---|---|
| 主项 | 按 A/B 分两段；B 段去掉 `N_q` |
| 修正 | `σ`、`L_cap`：登记量 |
| 登记量 | prefill / decode、`L_cap`、是否 varlen |
| 判据 | 固定 `k` 扫 `s`：A 路径线性、B 路径平坦 → 直接定段。HyFormer 的 `decode`（Q 与 KV 同为 `short_len`）与 `seq_cross`（KV 为 `kv_len`）正好构成这个对照 |

**参考**

- `npu_fusion_attention` 的稀疏与变长参数 — https://github.com/970334745/sam3.1-npu/blob/npu-adaptation/NPU_CAPABILITY_REPORT.md 🟡
- FlashAttention 的分块与 mask 跳过（决定 B 路径的 `σ`）— https://www.hiascend.com/developer/techArticles/20240607-1 🟢
- 分块 tiling 与负载均衡 — https://www.hiascend.com/developer/techArticles/20240920-1 🟢

## 5 组内注意力 · `group_attn`

**定义与主项。** `group_attn = B · R · T² · d`，`R = max(1, ⌊L/T⌋)`，`T` 为组大小（预填 16）。

**两条实现路径，复杂度差一个 L 次幂**

| 路径 | 做法 | 对 L 的指数 |
|---|---|---|
| A 批量 FA | 视作 `B·R` 条长度为 `T` 的独立序列，批量做 FA | `R·T² = L·T` → **∝ L** |
| B 全注意力 + 块对角落掩码 | 一次算 `L×L`，被完全 mask 的 tile 跳过 | `∝ L²`（跳过部分除外） |

**判定方法（先判后测，省一半样本）**

固定 `R` 只动 `L`（例如 `T` 固定、`L` 取 `R·T` 的整数倍）：

- 时间不随 `L` 变 → A（组独立，总工作量不变）
- 时间随 `L` 线性 → A（但组数在涨）
- 时间随 `L` 二次 → B

现有指南里 LONGER 的「次数接近 1 还是 2」正是这个判据，建议**把它从「拟合后看系数」提前到「测量前判定」**，可省掉两种形式各测一遍。

**最终式**

```
A: T ≈ B·(L/T)·T²·d / P_eff = B·L·T·d / P_eff + b
B: T ≈ B·L²·d·σ / P_eff + b        # σ ≈ 1/T（块对角）
```

**拟合口径**：主项保留 `token_square`；A/B 由判据定，不拟合；登记 `T`、组数是否随 L、是否融合。

**参考**

- FlashAttention 的 causal 块级跳过与负载均衡（决定 B 路径是否成立）— https://www.hiascend.com/developer/techArticles/20240607-1 🟢
- Tiling 的核间负载均衡（块数不能整除核数时的拖尾）— https://www.hiascend.com/developer/techArticles/20240920-1 🟢

## 6 token 轴矩阵乘 · `token_gemm`

**定义与主项。** 与组内注意力共用 `token_square` 与 `token_linear`；`groups_follow_length=False` 时**不读 `L`**。

**与 `group_attn` 的唯一差别**：是否有 `T²`。`token_gemm` 是组内的一次线性混合（组内 token 之间做矩阵乘但不做注意力），成本 `B·R·T²·d` 中 `T²` 来自组内两两相乘，`token_permute` 则是纯转置、无 `T²`。

**复杂度形式**

```
T ≈ B·R·T²·d / P_eff + B·R·T·d·s / BW + b
```

组数不随 L 变时，整项与 `L` 无关——这正是「ρ_L = 0」的情形，也说明**不是所有算子都能用 `L` 的幂描述**。

**拟合口径**：主项保留；`groups_follow_length` 是布尔登记量，决定 `R` 是否 `= L/T`；判据同 §5。

**参考**：同 §5；另见 MatMul 最佳实践（组内 GEMM 的分核与基本块）— https://www.hiascend.com/developer/techArticles/20240816-1 🟢

## 7 转置 / 重排 · `token_permute`

**定义与主项。** `B · T · d`，按字节计，**没有 `T²`**。无 Cube 参与。

**昇腾上的实现路径**

| 路径 | 做法 | 成本 |
|---|---|---|
| A 融合 | 被相邻 kernel 吸收（图编译的决定） | **≈ 0** |
| B 单独 kernel | 纯搬运 + UB 内重排 | `∝ Bytes`，受访存合并与 bank 冲突支配 |
| C TransData | 格式转换（ND↔NZ/NCHW↔5HD） | 官方口径：**通常比 Conv/MatMul 还耗时**，且常冗余 |

**优化手段 → 复杂度修正**

- **访存合并**：直接按线性地址转置时，同一 Warp 写到输出矩阵的不同行，GM 写无法合并，36.3 μs；用 UB 中转成 tile 后 28.2 μs（−22%）🟢。
- **UB bank 冲突**：32×32 tile 每行 128 B 恰跨 4 个 bank，转置读一列时集中落到两个 bank group。加 padding（32×34）后 23.9 → 15.2 μs（−37%）🟢。修正：`Bytes` 前乘 `1/η_bank`，`η_bank` 由 `d` 与 tile 宽的对齐关系决定。
- **纯搬运类算子的 VECIN/VECOUT 复用**：官方建议里明确列出 🟢。

**最终式**

```
T ≈ [融合 ? 0 : 2·B·T·d·s / (BW·η)]
```

**拟合口径**

| 项 | 处理 |
|---|---|
| 主项 | 保留 `permute` 列，但**引入二值登记 `fused`**：`fused=True` 时该项强制为 0 |
| 修正 | `η`（合并效率 × bank 效率）：由 `d` 与 tile 宽算出 |
| 判据 | 同一形状跑「融合前后」两版（或换编译器开关）：若时间不变 → 已融合；若差一倍 → 未融合 |

> 把 `permute` 当连续系数拟合，等于给一个**编译决策**配一个数值——这与 S22「不要为档位付参数」同一条理由。

**参考**

- SIMT 访存合并（Gather 与转置，4886 → 866 μs；转置 36.3 → 28.2 μs）— https://asc.gitcode.com/guide/operator_practice/simt_operator_optimization/memory_access/memory_access_merge.html 🟢
- 避免 UB bank 冲突（23.9 → 15.2 μs）— https://asc.gitcode.com/guide/operator_practice/simt_operator_optimization/memory_access/avoid_ub_bank_conflict_simt.html 🟢
- 格式转换优化（TransData 常比 Conv/MatMul 耗时，且存在冗余）— https://www.hiascend.com/doc_center/source/zh/canncommercial/700/modeldevpt/ptmigr/AImpug_000073.html 🟢

## 8 归一化与逐元素 ·（新增）`elemwise_reduce`

**为什么加。** 每层都有 LN/RMSNorm/SiLU/scale/mask-add。四套配方里一项都没登记，全部沉在截距里。这带来两个假象：截距随层数线性涨（被误认为「固定开销大」）、以及换模型时截距不可迁移（因为层数与 norm 类型都变了）。

**定义与主项**

```
T ≈ 2 · B · L · d · s / BW_eff        # 读一遍 + 写一遍；归约另有 O(L) 的中间量
```

主导资源是 Vector 与 MTE，不是 Cube。**没有 L 的幂，只有字节数**。

**已与官方 HSTU 核对（这条最反直觉）**：官方在 `qk_attn * mask` 之前做了一次 `F.silu`，
作用在 `(B, H, L, L)` 上——元素数 `B·H·L² = 2,097,152`，而 qkᵀ 的乘加是 33.5M。
即这一项是 L² 阶，是 qkᵀ 的 `1/d_head`；**若按 `B·L·d` 记（65,536）会低估 32 倍**。
因此 `elemwise` 必须允许两项：`elemwise_linear`（按元素数）与 `elemwise_square`（按 L²）。

**昇腾上的实现路径**

| 路径 | 做法 | 成本 |
|---|---|---|
| A 融合进相邻 kernel | 官方首选：把 RMSNorm/LayerNorm/Softmax 融进同一 kernel，避免中间结果写回 GM | ≈ 0（只剩寄存器/UB 操作） |
| B 独立 kernel | 逐行切分、多核并行、double buffer | `∝ Bytes` |
| C 逐核串行 | 未按行切分，只用 1 个 Vector Core | `∝ Bytes × 核数` |

**优化手段 → 复杂度修正**

- **多核按行切分**：RmsNormQuant 从 1 核改 64 核，6790 → 113.6 μs（**59.8×**，利用率 93.4%）；再加寄存器数据流与 double buffer，最终 7693 → 49.0 μs（**157×**）🟢。修正：`Bytes/(BW·核数利用率)`。
- **临时 Buffer 共享**：Softmax 高阶 API 的临时空间会挤占其它计算的 UB，导致单次搬运量减半、搬运次数翻倍；共享后搬运次数 16 → 8 🟢。修正：`Bytes` 前乘 `1 + UB占用率`。
- **`gamma` 常驻 UB**：跨行共享的权重若在循环内重复搬运，等于把 4096 次同样的 16 KB 白搬 🟢。修正：`B·d`（而非 `B·L·d`）的权重项，可忽略。

**最终式**

```
T ≈ [A: 0]
    [B: 2·B·L·d·s / (BW·核数利用率·(1+UB占用率))]
    [C: 同上 × 核数]
```

**拟合口径**

| 项 | 处理 |
|---|---|
| 主项 | **不新增拟合项**。A 路径成本≈0，B 路径并入截距或 `linear` 的字节项 |
| 登记量 | `fused`（二值）、`n_layers`、norm 类型 |
| 判据 | 同一模型关掉融合（图优化开关）跑一次：时间差即为该段；若差 < 2%，全为 A 路径 |

> **这条最值得先做的原因**：它把「截距随层数线性涨」这一现象解释掉了一大半。若 A 路径成立，`b` 里就不该有 `n_layers × 每层 norm 时间`；若有，说明融合没生效，是**可优化项**而不是模型参数。

**参考**

- CV 融合算子基础（为什么融合；FA 就是 MatMul+Scale+Mask+Softmax 融合）— https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/900beta2/opdevg/Ascendcopdevg/atlas_ascendc_10_0049.html 🟢
- RmsNormQuant 分阶段优化（1 核 → 64 核 59.8×；寄存器数据流；double buffer；总 157×）— https://cann.csdn.net/6a15a2e910ee7a33f2755b2e.html 🟡

## 9 门控与 top-k ·（新增）`moe_gate`

**为什么加。** gating 输出 `N_exp` 维分数再取 top-k。成本由**专家数**决定，与 `L` 无关；若塞进 `L` 的幂律里，会得到一个既非 0 也非 1 的假指数。

**定义与主项**

```
T_gate ≈ B·L·N_exp·s/BW  (打分)  +  topk( B·L·N_exp )  (排序/选择)  +  元数据写出 O(B·L·k)
```

`N_exp` 通常 64–256；`k` 通常 6–8。

**昇腾上的实现路径**

| 路径 | 做法 | 成本 |
|---|---|---|
| A 融合算子 | `aclnnMoeGatingTopKSoftmax`：Softmax 与 TopK 合成一个算子，一次输出概率、专家索引、行索引 🟢 | 单 kernel |
| B 串行小算子 | softmax → topk → gather，各自下发 | 3 个 kernel + 中间张量往返 |
| C 含重排 | 再加 `MoeTokenPermuteWithEP`：双重排序 + 索引拷贝，规避 AICPU 上的 `FloorDiv` 🟢 | 融合后 **3.5×** |

**复杂度修正**

- `renorm` 参数决定「先 softmax 再 topk」还是「先 topk 再 softmax」——后者只需对 `k` 个值做 softmax，`O(k)` 而非 `O(N_exp)` 🟢。**这是一个登记位，不是拟合参数。**
- 重排若走 B 路径，`FloorDiv` 落在 AICPU 上，成为瓶颈（3.5× 收益的来源）🟢。
- `finished` 标记（对应行已结束）会直接填 `num_expert`，不影响复杂度，但影响索引分布。

**最终式**

```
T ≈ B·L·(N_exp·s/BW + c_topk·log N_exp) + b_kernel_count
renorm=1 时第一项降为 B·L·k·s/BW
```

**拟合口径**

| 项 | 处理 |
|---|---|
| 主项 | `B·L·N_exp`（新增一条轴）；`renorm` 登记 |
| 登记量 | `N_exp`、`k`、`renorm`、路径 A/B/C |
| 判据 | 固定 `L`、改 `N_exp`（64→256）：线性 → 打分主导；平坦 → 排序主导。改 `renorm`：差异 ≈ `(N_exp−k)/N_exp` 的字节量 |

**参考**

- `aclnnMoeGatingTopKSoftmaxV2` 接口（renorm 两种顺序、finished 行、输出三件套）— https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/81RC1beta1/API/aolapi/context/aclnnMoeGatingTopKSoftmaxV2.md 🟢
- MoE 重排/反重排融合算子（双重排序规避 FloorDiv，3.5× / 3.8×，整网吞吐 +3–6%）— https://www.hiascend.com/developer/techArticles/20250702-1 🟢

## 10 专家分发 / 合并 ·（新增）`moe_comm`

**为什么加。** EP>1 时每层一次 AllToAllV，是 GR 推理最容易超时的一段；而且它是**变长**的，`τ` 不再是常数。

**定义与主项**

```
T_comm ≈ n_round·α + (k·B·d·s·(EP−1)/EP)/BW_eff   +  元数据(路由表)开销
```

注意 `(EP−1)/EP` 与 CP 的 `(N−1)/N` 同形——这也是为什么 §10 里 κ 与 v 会共线，与本文 §4 的二维平面退化是同一件事。

**昇腾上的实现路径**

| 路径 | 做法 | 成本特征 |
|---|---|---|
| A RDMA 全互联 | 每个 token 直发目标卡 | 通信量最大，`∝ topk` 且 `∝ EP` |
| B AIV+AICPU 分层 | 同号卡组走 RDMA，其余经同号卡机内中转 | 官方示例：BS=16、H=7168、topK=8、FP16，全互联 1.75 MB / 86.1 μs → 分层 0.766 MB(跨机) + 1.53 MB(机内) / 46.3 μs 🟢 |
| C 通算融合 | `MoeDistributeDispatch` / `MoeDistributeCombine`：路由下沉 Device、AIV 直驱 RDMA、计算与通信流水 | 推理吞吐 **+50%** 🟢 |

**由官方示例反推的 `v`（本工作推导）** 🔵

| 跨度 | 通信量 | 时间 | 等效 `v⁻¹` |
|---|---|---|---|
| 跨机（RDMA，分层后） | 0.766 MB | 38.3 μs | **≈ 20 GB/s** |
| 机内（HCCS 中转） | 1.53 MB | 8.0 μs | **≈ 191 GB/s** |
| 全互联（纯 RDMA） | 1.75 MB | 86.1 μs | ≈ 20 GB/s |

**结论：`v` 不是常数，跨机与机内差约 10 倍。** 现有形式里 `v` 是一个标量，等价于假定通信域只有一种跨度。对 8 卡单机（MTGR 的 CP 就在单机内）这个近似可接受；一旦跨机，`v` 必须按跨度分两档——这是「三个参数不够」之外的另一条理由。

**最终式**

```
T ≈ n_round·α + Σ_{跨度∈{机内,跨机}} V_跨度 / BW_跨度   + 元数据
n_round: Ring = N−1, Butterfly = log₂N, AllToAllV = O(1) 轮但变长
```

**拟合口径**

| 项 | 处理 |
|---|---|
| 主项 | `v·V` 保留，但 `v` 按跨度分档；`τ` 改为 `n_round·α`，`n_round` 登记为算法函数 |
| 登记量 | 算法（Ring/Butterfly/AllToAllV）、跨度、`topk`、`EP` |
| 判据 | 同一 `V` 下改 `EP`（2→8）：若时间按 `log₂EP` 阶梯涨 → 轮数主导，`α` 项成立；若线性涨 → 带宽主导 |

## 11 全库打分 ·（新增，范围待定）`score_gemm`

**为什么加，以及为什么标「待定」。** 推荐的最后一步是「用户向量 × 全库向量」，`N_item` 百万级，形状与前面所有算子都不同（`M` 极小、`N` 极大、`K` 中等）。若本工作的「一次前向」只算到生成 item id 为止，则不在范围内；若含召回/排序段，则它是整条链路里最贵的一项，必须单列。

**定义与主项**

```
T ≈ N_user · N_item · d · s / BW_eff      # M 小 N 巨大 → 流式，带宽 bound
```

**与 `linear` 的本质差别**：`linear` 的 `N_tok·d` 项会让它落在 Cube；`score_gemm` 的权重矩阵（`N_item·d`）远大于 L1/L2，每个元素只用一次，**加权最小二乘意义下的算术强度极低**，必然带宽 bound。分块策略也不同：按 `N_item` 切，token 常驻。

**优化手段 → 复杂度修正**

- 按 `N_item` 分块 + 权重常驻 L1（官方建议：「较小矩阵长驻 L1，仅分次搬运较大矩阵」）🟢。
- `N_item` 侧对 512B 对齐敏感（一次搬大块）🟢。
- 量化（fp16 → int8）：`Bytes` 减半，时间近线性下降。
- 采样 / 近似检索（IVF、HNSW）：把 `N_item` 换成 `N_probe`——**这是算法层选择，不是实现优化**，必须在登记表里写明。

**最终式**

```
T ≈ N_user·N_item·d·s / (BW·η)      # η 由 512B 对齐与分块决定
采样时：N_item → N_probe
```

**拟合口径**

| 项 | 处理 |
|---|---|
| 主项 | 新增 `N_user·N_item·d` 列；若采样，登记 `N_probe/N_item` |
| 登记量 | 是否采样、数据类型、`N_item` |
| 判据 | 固定 `N_user` 改 `N_item`：严格线性 → 带宽 bound 成立；出现台阶 → 分块与对齐在起作用 |

**参考**

- MatMul 最佳实践（较小矩阵常驻 L1、大包搬运、分核）— https://www.hiascend.com/developer/techArticles/20240816-1 🟢
- 优化建议总览表（一次搬大块、512B 对齐、L2CacheMode）— https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/900beta2/opdevg/Ascendcopdevg/atlas_ascendc_best_practices_10_00010.html 🟢
- 910B 规格（HBM 1.2–1.6 TB/s、L2 192 MB）用于估 `η` 上限 — https://hwcomputing.csdn.net/6aa8af828f401d3626604ea1.html 🟡

## 附录 A：十一个算子的资源归属

| 主导资源 | 算子 | 共同特征 | 对拟合的含义 |
|---|---|---|---|
| **Cube** | linear、self_attn（大 L）、cross_attn（prefill）、group_attn、token_gemm | 成本 ∝ FLOPs，受分块与波次量化 | 用 tile 计数或 FLOPs 项，慎用单幂律 |
| **MTE / 带宽** | lookup、token_permute、score_gemm、self_attn（小 L）、elemwise | 成本 ∝ Bytes，受访存合并与对齐支配 | 用字节项，系数是「每字节时间」 |
| **Vector** | elemwise、moe_gate（打分段） | 成本 ∝ 元素数，受核数利用率支配 | 并入字节项或截距 |
| **Scalar / 下发** | moe_gate（排序段）、所有算子的 per-kernel 开销 | 成本 ∝ kernel 数，与形状无关 | **截距，直接测，不拟合** |
| **通信** | moe_comm、（CP/TP/EP 的缩放项） | 成本 = 轮数×α + 字节×β | τ 随 `n_round` 变，`v` 按跨度分档 |

**这张表解释了一切「指数漂移」**：同一算子在资源归属切换处，指数就变一次。self_attn 从 MTE 切到 Cube（约 `L_star`），linear 从 A 路径（权重搬运）切到 B 路径（计算），都是同一机制。
